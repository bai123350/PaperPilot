# 对话操作卡与报告等待区设计

## 背景

PaperPilot 当前在研究运行页面采用双栏布局：左侧为持久化研究对话，右侧在运行中展示九阶段进度、百分比和运行信息，完成后展示报告。用户希望把大模型与研究流水线执行的操作像 Codex 一样呈现在对话区中；右侧在运行期间保持安静等待，完成后只呈现最终报告。

本设计覆盖首次研究运行、完成后的证据追问和报告修订。操作记录需要持久化，在刷新页面或重新进入项目后仍可查看。

## 目标

1. 在研究对话中按时间展示真实、细粒度、可持久化的执行操作。
2. 每项操作使用独立完整卡片，展示状态、安全摘要、数量、耗时和时间。
3. 运行中将右侧简化为报告等待态，完成后原位切换为完整报告。
4. 让首次运行、证据追问和报告修订共享同一套可审计操作模型。
5. 保持用户与项目隔离、删除级联、日志隐私和报告证据约束不变。

## 非目标

- 不展示模型 chain-of-thought、隐藏推理、完整提示词或原始模型响应。
- 不展示论文正文、Evidence Record 原文片段或研究问题原文。
- 不把操作记录当成系统日志，也不写入 Redis。
- 不改变固定九阶段流水线、报告结构、恰好三个 Recommendation 或证据覆盖约束。
- 不在本次改造中引入新的任务系统、微服务或外部可观测平台。

## 方案选择

采用独立持久化的 `RunOperation` 模型。操作不伪装成对话消息，也不由前端根据阶段临时推断。

未采用的方案：

- 将操作保存为系统对话消息：会混淆用户可读回复和执行审计记录。
- 由前端根据九阶段生成临时卡片：无法表达真实数量、耗时、失败和刷新后的历史。
- 继续使用 `research_runs.events` JSON：缺少稳定标识、关联关系、查询顺序和可迁移的版本化合同。

现有 `research_runs.events` 保留以兼容旧阶段 SSE；新界面以 `run_operations` 为事实来源。

## 数据模型

新增 `run_operations` 表及 `RunOperationEntity`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `String(36)` | 操作稳定标识 |
| `run_id` | FK | 关联 Research Run，删除时级联 |
| `sequence` | `Integer` | Run 内单调递增顺序 |
| `task_kind` | `String(24)` | `research_run`、`discussion` 或 `report_revision` |
| `operation_kind` | `String(48)` | 受控操作类型 |
| `stage` | `String(32) nullable` | 可选的九阶段映射 |
| `title` | `String(160)` | 由服务端模板生成的短标题 |
| `summary` | `String(500)` | 由服务端模板生成的安全摘要 |
| `status` | `String(16)` | `running`、`completed` 或 `failed` |
| `metrics` | `JSON` | 受白名单限制的计数和耗时数据 |
| `conversation_message_id` | FK nullable | 可选的对话轮次关联 |
| `started_at` | `DateTime` | 开始时间 |
| `completed_at` | `DateTime nullable` | 终止时间 |

数据库约束：

- `(run_id, sequence)` 唯一。
- `run_id` 与可选的 `conversation_message_id` 均使用级联删除。
- 操作记录只能从 `running` 进入 `completed` 或 `failed`；终止状态不可改回。
- 重试创建新的操作记录，不覆盖上一次失败记录。

`metrics` 只允许数值或受控枚举，例如 `candidate_count`、`retained_count`、`evidence_count`、`source_count` 和 `duration_ms`。禁止任意文本键值。

## 领域事件与持久化

新增结构化 `OperationUpdate` 领域合同，并在流水线和对话服务中通过回调发出：

1. 动作开始时创建 `running` 记录。
2. 动作完成时更新同一记录为 `completed`，写入白名单 metrics 和完成时间。
3. 动作失败时更新为 `failed`，摘要使用服务端安全错误映射。

首次研究运行至少产生以下真实操作：

- 结构化研究问题。
- 分别检索每个文献源并记录候选数量。
- 标识归一化与去重并记录前后数量。
- 相关性筛选并记录保留数量。
- 全文或摘要解析并记录成功数量。
- 创建 Evidence Record 并记录数量。
- 研究综合。
- 生成三个下一步建议。
- 引用审计。
- 保存最终报告。

证据追问至少产生：

- 定位当前 Run 的相关 Evidence Record。
- 基于已纳入证据生成回复。
- 核验回复引用的 evidence ID。
- 保存助手回复。

报告修订至少产生：

- 定位当前证据和报告版本。
- 生成候选修订。
- 校验主要 Claim 证据覆盖与恰好三个 Recommendation。
- 保存新报告版本。

Demo mode 使用相同事件序列和确定性 metrics，保证无外部 API Key 时可复现。

## API 合同

新增版本化只读接口：

`GET /v1/runs/{run_id}/operations`

响应：

```json
{
  "contract_version": "1.0",
  "operations": []
}
```

所有查询先通过 `run_id` 与认证用户的 `user_id` 联合验证归属，再返回操作。

扩展现有 `GET /v1/runs/{run_id}/events` SSE：

- 保留兼容的 `stage` 和 `done` 事件。
- 新增 `operation` 事件，payload 使用同一 `RunOperation` schema。
- SSE 事件 ID 使用操作的稳定 ID；客户端断线后先重新读取持久化操作列表，再继续订阅。
- SSE 不发送研究问题、论文正文、证据片段、提示词或完整模型响应。

前端 API client 新增显式的 `RunOperation`、`RunOperationList` 类型和操作事件订阅函数，不在页面组件内复制合同。

## 前端信息架构

### 桌面端

页面保持双栏：

- 左侧为固定宽度的研究对话区，普通消息与操作卡按创建时间合并排序。
- 每个操作使用独立完整卡片，不折叠为九阶段轨道。
- 右侧占据主要阅读宽度。
- 运行中右侧只显示“报告准备中”的安静等待态。
- 完成后右侧原位切换为完整报告及打印、Markdown 操作。

操作卡包含：

- 对应阶段的 Lucide 图标。
- 动作标题。
- `进行中`、`已完成` 或 `失败` 状态。
- 安全摘要。
- 数量、耗时等白名单指标。
- 开始或完成时间。

进行中的卡片使用轻量动画，且遵守 `prefers-reduced-motion`。完成卡保持完整可见。失败卡显示安全错误摘要；首次运行失败时提供重试入口。

### 移动端

- 运行中：对话与操作卡在前，报告等待态在后。
- 完成后：完整报告提升到首位，对话历史放在报告之后。
- 操作卡使用单列指标，长标题和数字允许换行，不产生横向滚动。
- 移动底部导航不得覆盖输入框、操作卡或报告内容。

### 时间排序

对话消息和操作记录使用服务端时间排序；相同时间时按操作 `sequence` 和稳定 ID 排序。乐观发送的用户消息和流式助手占位消息保留现有行为，不写入持久化操作列表。

## 状态与错误处理

- `queued/running/waiting/retrying`：右侧显示报告等待态。
- `completed`：右侧显示最终报告。
- `failed/cancelled`：右侧显示未生成报告的简洁状态，详细安全错误位于左侧最后一张操作卡。
- 首次运行重试：保留失败操作历史，并追加新的重试操作。
- 追问失败：不影响已有报告和历史操作，对话输入仍可再次发送。
- 报告修订失败：保留上一报告版本，不创建半成品 revision。
- SSE 断开：客户端回退到持久化接口刷新；按操作 ID 去重。
- 页面刷新：先读取 Run、Conversation、Operations，再恢复流式订阅或轮询。

## 隐私与安全

- `title`、`summary` 和 `metrics` 由服务端模板生成，不接受模型自由文本直接透传。
- 模型仅能返回已有 evidence ID；未知或跨项目 ID 继续被拒绝。
- API、SSE、日志和监控禁止记录研究问题、论文正文、Evidence Record 片段、提示词、模型完整响应、密钥或令牌。
- 日志只记录 run ID、operation ID、operation kind、阶段、状态、耗时和安全错误类别。
- 项目删除通过外键级联删除操作记录，并继续执行现有对象、正文、向量、缓存和中间产物清理。

## 测试策略

### 后端

- Alembic migration 创建表、索引、唯一约束和外键级联。
- Operation 状态迁移和重试追加行为。
- Pipeline 在正确顺序发出操作，并报告准确计数。
- Demo mode 产生确定性操作序列。
- Operations API 的用户与项目隔离。
- SSE 只返回安全 schema，能发送实时操作与终止事件。
- 项目删除级联清除操作。
- 追问和报告修订分别产生操作；失败修订保留上一版本。
- 白名单序列化拒绝未允许字段和任意文本 metrics。

### 前端

- 操作卡正确渲染运行、完成和失败状态。
- 消息与操作按时间稳定排序并按 ID 去重。
- 运行中右侧只显示等待态，不显示九阶段轨道和百分比。
- 完成后显示报告及导出操作。
- 失败时显示重试入口且不泄露非安全错误。
- SSE 中断后从持久化数据恢复。
- 移动端完成后报告优先，且无横向溢出或底部导航遮挡。

### 回归验证

根据仓库要求运行：

- 后端 pytest 与 ruff。
- 前端单测与 lint。
- 生产构建和 TypeScript 检查。
- 桌面与移动 E2E。
- Alembic migration 测试和 `docker compose config --quiet`。

## 完成标准

1. 首次研究、追问和报告修订均产生真实、持久化的细粒度操作。
2. 刷新或重新进入项目后操作顺序、状态和指标一致。
3. 运行中右侧只出现报告等待态；完成后只呈现最终报告内容与报告操作。
4. 操作卡不包含禁止字段，跨用户无法读取。
5. 失败、重试和 SSE 断线不造成操作丢失、重复或报告版本损坏。
6. 桌面与移动主流程测试通过，现有证据与报告不变量保持成立。
